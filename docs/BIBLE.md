# MindAttic.Unity.Multiplayer — Project Bible
> Single source of truth for what MindAttic.Unity.Multiplayer IS, is NOT, and the rules that keep it coherent.
> README says how to use it; [RFC 0001](rfc/0001-architecture.md) holds the design and build order; this says how to think about the system.

Status legend: ✅ done (verified by a test/build) · 🟡 partial · ⬜ planned · `living`.

## 1. The one sentence {#UM-§1}
MindAttic.Unity.Multiplayer is a Unity 6 package that gives any MindAttic game server-authoritative multiplayer, written as attribute-decorated partial methods and fields, in either a listen-server or a dedicated-server topology, joined by IP:port or a join code.

## 2. The product promise {#UM-§2}
- A game adds one local package and one `NetBootstrap` component, marks methods `[ToServer]` / `[ToClients]` / `[ToOwner]` / `[ToClient]` and fields `[Synced]`, and is networked.
- The same game code runs as host, dedicated server or client; the topology is configuration, not code.
- A player who drops and reconnects gets the same seat back.

## 3. What it is NOT {#UM-§3}
- NOT a netcode engine. Netcode for GameObjects 2.x and Unity Transport 2.x do the transport and replication; this package is the API and policy on top.
- NOT client-authoritative. There is no client-side prediction of shared state; see [UM-LAW-1](#UM-LAW-1).
- NOT reflection-based. RPC plumbing is generated at compile time by the package's source generator, never discovered at runtime.

## 4. Architecture canon {#UM-§4}
The full layout lives in [RFC 0001 § Architecture](rfc/0001-architecture.md#architecture) and is not repeated here ([UM-LAW-4](#UM-LAW-4)). The assembly boundary that the laws below depend on:

```
MindAttic.Unity.Multiplayer.Core     Runtime/Core   noEngineReferences; no UnityEngine, no Unity.Netcode
        ▲
MindAttic.Unity.Multiplayer          Runtime        the NGO adapter: the only runtime assembly that imports Unity.Netcode
        ▲
MindAttic.Unity.Multiplayer.UI       Runtime/UI     optional drop-in front end (only with MindAttic Components); NetBootstrap/NetSession only, no Unity.Netcode
MindAttic.Unity.Multiplayer.Editor   Editor         editor tooling
MindAttic.Unity.Multiplayer.Testing  Testing        the test kit games reference from their PlayMode tests (Editor and test builds only)

MindAttic.Unity.Multiplayer.UI.Tests Tests/UI       PlayMode suites for the front end
MindAttic.Unity.Multiplayer.Editor.Tests  Tests/Editor  EditMode suites for the editor tooling
game code                            (consumer)     talks to NetSession / NetEntity / attributes only
```

## 5. The Laws {#UM-§5}

MindAttic.Unity.Multiplayer **inherits the org-wide house rules** in
[`../../MindAttic.HouseRules.md`](../../MindAttic.HouseRules.md). Of note here: [HOUSE-LAW-1] (whole-number versioning: the package is `0.0.0` until the v1.0.0 tag in UM-T20), [HOUSE-LAW-8] (done is verified, not asserted), [HOUSE-LAW-13] (LF-only, enforced by the root `.gitattributes`).

Project-specific laws:

### UM-LAW-1 — The server owns state {#UM-LAW-1}
Every piece of shared game state is written only on the server. Clients send intent (`[ToServer]` calls); the server validates it, applies it and replicates the result (`[Synced]` fields, `[ToClients]` / `[ToOwner]` / `[ToClient]` calls). A client never asserts an authoritative value, and the generator and analyzers reject client writes to `[Synced]` state.

### UM-LAW-2 — Nothing above the NGO adapter imports Unity.Netcode {#UM-LAW-2}
`Unity.Netcode` (and `Unity.Networking.Transport`) are referenced only by the adapter assembly `MindAttic.Unity.Multiplayer` and its Editor, Tests and Testing (test kit) companions. `MindAttic.Unity.Multiplayer.Core` is engine-free (`noEngineReferences`), and game code sees only MindAttic types (`NetSession`, `NetEntity`, `NetSender`, the attributes). Generated code is the one sanctioned exception: it is emitted into the game's assembly by the generator and is not hand-written there. Swapping the backend means rewriting the adapter, nothing else.

### UM-LAW-3 — Generator output is C# 9 {#UM-LAW-3}
The source generator emits only C# 9 constructs (extended partial methods, no file-scoped namespaces, no record structs, no `required`, no raw string literals), so its output compiles on every Unity 6 compiler. It targets netstandard2.0 against Microsoft.CodeAnalysis.CSharp 4.3.x.

### UM-LAW-4 — One home per fact {#UM-LAW-4}
Every fact lives in exactly one place and everything else links to it. Dependency versions live in `package.json`; the design and ticket order live in RFC 0001; laws live here; story status lives in [USER_STORIES.md](USER_STORIES.md). A second copy is a bug.

Routes, header and JSON field names live in Core's `RendezvousProtocol` so UM-T13's client shares them: `POST /v1/register` `{secret, address?, port, transport?}` → 201 `{code, token, ttlSeconds, expiresAt}` (an omitted address means the caller's own; `JoinTarget.ForEndpoint` rejects wildcards, whitespace and port 0), `POST /v1/heartbeat` `{code, token}` renews for another TTL, `GET /v1/resolve/{code}` → `{code, address, port, transport}` (player-typed forms accepted through `JoinCode.TryParse`; 400 with the parse reason, 404 for unknown or expired), `DELETE /v1/register/{code}` with `X-Rendezvous-Token`, and `GET /healthz` (Degraded when full, never rate limited). - ✅ Drop-in front end (UM-T48): the optional `Unity.Multiplayer.UI` assembly (`Runtime/UI`), compiled only when `com.mindattic.components.unity` is installed (`versionDefines` → `MINDATTIC_COMPONENTS`, required by its define constraint) and using `com.mindattic.unity.shared` profiles when present (`MINDATTIC_SHARED`); `package.json` cannot list `file:` packages, so a game adds both manifest lines itself. `NetFrontEnd` (one component beside the `NetBootstrap`; *MindAttic ▸ Multiplayer ▸ Add Front End*, `NetFrontEndSetup.Run`, networks the scene first and adds it, or changes nothing and names the exact manifest lines missing) builds, entirely from MindAttic Components: a main menu (Host, Join by IP, Join by code, Settings with name and colour, the game's items, Quit), a host lobby (the grouped join code in a `MaCodeDisplay` with Copy, or the LAN address when no code could be published; a live roster from the seats with colour swatches, a Host tag, held seats as "reconnecting...", remove with confirm; Leave/Start), a cancellable busy dialog while hosting or joining, a dialog per disconnect reason, an automatic reconnect for a lost connection (same address or code again, same player token, so the same seat; progress and Cancel; refusals and kicks are final) and an in-game Esc menu (Resume, Invite players, Settings, the game's items, Leave/End game). - ✅ Votes kit (UM-T54, promoted from Unity.Cursory's UC-T10): Core `VoteBox` (engine-free; one vote at a time over a roster of client ids; the starter's Yes; passes when Yes reaches the quorum and runs the kind's server-side effect first; rejected as soon as the quorum is unreachable; lapses on the `ITickClock` with a per-second countdown; a leaver dropped and the quorum recomputed, the last one abandoning it; `Cancel`), `VoteRules` (quorum fraction, default 2/3 rounded up; timeout, default 15 s; optional per-starter cooldown after a failed vote; `MayStart`; `StarterVotesYes`), `VoteKind` (id, `Title`/`Description` worded from the request, `Check` with the starter's reason, `MayVote`, `Passed`, per-kind quorum and time), `VoteRequest` (a `long` and `string` payload), `VoteStatus`, `VoteResult`, `VoteStartResult`/`VoteRefusal` and `VoteText` (the overlay's words, their one home). - ✅ Player roster and identity (UM-T55): `NetSession.Roster` (`NetRoster`) gives every peer one Core `NetPlayer` per seat (seat, client id, name, colour, host, connected, ping, local), built by the server from its seats (`NetPlayer.FromSeat`: `PlayerNames.Clean`ed name, `PlayerColors.Resolve`d colour with the seat's palette colour for an unpicked white) and kept in step over named messages (`MindAttic.Multiplayer.Roster*`): a client says hello once connected and gets a full `RosterUpdate`, then incremental ones from `PlayerRoster.Replace`'s differences; a held seat stays as not connected and a reconnect keeps seat and record; the server probes each client's round trip once a second (first one interval after it joined). `RequestChange` is checked by the server (`PlayerChangeRequest.Validate`: `PlayerNames.Validate`, opaque `PlayerColors.Validate`, a rate limit) and an accepted change is stored with `SeatRegistry.Rename` and in `NetSession.Identity`. `NetFrontEnd`'s lobby reads the roster, its Settings renames mid-game through the server, and an accepted local change is saved to the `IPlayerIdentitySource`. Verified by `dotnet test tests/Core.Tests` (PlayerNamesTests, PlayerColorsTests, PlayerRosterTests, RosterWireTests) and `tests/run-playmode.ps1` (`RosterTests`: host and two clients, late join, round trips, rename everywhere, bad names refused by the server, reconnect keeps identity, kick; `NetFrontEndTests`: the lobby follows a mid-game rename and the profile is saved). - ✅ Networked objects by key (UM-T60): a `NetKey` on a network prefab's root carries a game-given key (`NetKeys`: non-empty, at most 128 characters, no control characters or edge whitespace, ordinal) inside the object's spawn (NGO `OnSynchronize`), so every peer, late joiners included, knows it before any `OnSpawned`; it cannot change while spawned. `NetSession.Objects` (`NetRegistry`, also `NetRegistry.Current`) indexes spawned keyed objects on every peer over Core's `NetKeyTable<T>` (one holder per key, removal only by the holder): `TryGet<T>`/`TryGet(GameObject)`/`Get<T>`/`Contains`/`Keys`/`All`, `Spawned`/`Despawned` after every component's `OnSpawned` and before any `OnDespawned`, and server-side `Spawn(prefab, key, ...)` (refuses a bad or held key before anything spawns) and `Despawn(key)` (frees the key at once). An object spawned another way with a missing or duplicate key is logged on every peer and left out. Verified by `dotnet test tests/Core.Tests` (NetKeysTests, NetKeyTableTests) and `tests/run-playmode.ps1` (`NetRegistryTests`, Host and dedicated Server with two clients: lookup on every client, late join, out-of-order spawn and replacement, despawn and same-frame respawn, duplicate keys). ## 8. Glossary {#UM-§8}
- **NGO** — Netcode for GameObjects, Unity's GameObject netcode package.
- **Adapter** — the `MindAttic.Unity.Multiplayer` assembly; the only runtime code that touches NGO.
- **Listen server / host** — one player's game is also the server.
- **Dedicated server** — a headless server build everyone joins.
- **Join code** — a short, checksummed code resolved to a relay allocation or an IP:port.
- **Seat** — a player's slot on the server, kept across reconnects.
